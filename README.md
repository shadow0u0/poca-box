# 小卡櫃 · K-pop 小卡收藏管理

在 **iPhone、iPad、PC 上都能用**的小卡收藏管理 App。一份程式碼、三個平台，不需要 App Store 審核，也不需要 Apple 開發者帳號。

**未開啟雲端同步時，所有小卡資料與照片都只存在你自己的裝置上**，不會上傳到任何地方。
開啟同步並用 Google 帳號登入後，小卡資料會同步到 Firestore，照片存放在 Cloudflare R2，兩邊都由安全規則／權杖驗證限定只有你的帳號讀得到 —— **但空間的管理者在後台看得到**，而且**空間是邀請制的**（見〈誰可以使用這個雲端空間〉）。同步是可選的，不登入就維持純本機。

## 安裝到你的裝置

網頁本身是一般網址，用瀏覽器開啟就能用；但**安裝到主畫面**才會變成有 icon、全螢幕、可離線開啟的獨立 App，而且能大幅降低系統清除資料的機率（見下方「重要」）。

| 裝置 | 步驟 |
| --- | --- |
| **iPhone / iPad** | 用 **Safari** 開啟網址 → 點下方（或右上）的「分享」<kbd>􀈂</kbd> → 往下找到 **加入主畫面** → 加入 |
| **Windows / Mac（Chrome / Edge）** | 開啟網址 → 點網址列右側的「安裝」圖示 <kbd>⊕</kbd>，或選單 → **安裝「小卡櫃」** |
| **Android** | Chrome 開啟網址 → 選單 → **安裝應用程式** |

> iPhone 與 iPad 必須用 **Safari** 安裝，Chrome for iOS 沒有「加入主畫面」的 PWA 支援。

### ⚠️ 重要：請定期匯出備份

資料存在瀏覽器的本機資料庫裡。iOS Safari 對「**沒有安裝到主畫面**、又長期沒開啟」的網站，可能會清除其本機資料。App 已經做了兩層防護：

1. 啟動時自動申請「持久化儲存」授權（`navigator.storage.persist()`）；
2. 設定頁會在沒拿到授權時顯示提醒。

但真正的保險是**設定 → 匯出備份**，會下載一個 `pocabox-backup-日期.zip`（包含所有資料與照片）。請定期匯出，存到 iCloud、Google Drive 或電腦裡。

## 功能

- **小卡資料**：名稱、收藏時間、來源、團體、成員、專輯／活動出處、卡種、持有狀態、取得價格與幣別、自由備註
- **正面 + 背面照片**：列表顯示正面，詳情頁可點擊翻面。上傳時自動壓縮（可在設定調整品質）
- **完全自訂的分類**：來源、卡種、持有狀態、團體、成員、專輯都能自己新增。**在新增小卡的表單裡直接打一個不存在的名字就能當場建立**，不用先跑去設定頁
- **三種歸檔方式**
  - 卡片牆 + 多維度篩選與搜尋（篩選條件會寫進網址，回上一頁不會消失）
  - 團體 → 成員階層瀏覽
  - 自訂收藏夾，一張小卡可同時屬於多個收藏夾
- **團體全員套卡**：選團體即自動依成員產生格位，自動計算 `已收集 / 總數` 進度並列出還缺誰
- **備份與跨裝置搬移**：匯出／匯入 zip，匯入時可選「合併」或「完全覆蓋」
- **離線可用**、深色／淺色主題

### 跨裝置怎麼同步？

設定 → 雲端同步 → 用 Google 帳號登入，三台裝置就會自動同步，不需要再手動搬備份。
**雲端空間是邀請制的** —— 見下面的〈誰可以使用這個雲端空間〉。

| 資料 | 放哪 |
| --- | --- |
| 小卡、團體、收藏夾等文字資料 | Firestore `users/{uid}/{表}/{id}` |
| 照片原圖與縮圖 | Cloudflare R2，經 `worker/` 這支 Worker 代理 |

- **合併規則**：`updatedAt` 較新者勝，軟刪除一併傳播 —— 與備份匯入用的是同一套語意。
- **待送清單靠水位線，不靠佇列**：`updatedAt` 比「上次成功推送」新的就是還沒送的，
  離線期間的修改自然包含在內，所以沒有 outbox 表要維護。
- **照片是縮圖優先**：新裝置先抓縮圖（每張約 15KB）讓列表立刻能用，原圖在背景補齊。
  補原圖時**不會動 `updatedAt`** —— 那是純本機動作，一改就會反向覆蓋雲端。
- **兩邊都是即時的**：本機改動由 `localWrites.ts` 監看，去抖 1.5 秒後推送（實測 1.6 秒）；
  別台的改動則靠 `users/{uid}/meta/pulse` 這份心跳文件的 `onSnapshot` 通知（實測 2 秒）。
  監聽器只負責說「有東西變了」，實際抓取與合併仍走原本的 `pull` —— 套用遠端資料的
  路徑只有一條，不是兩條。
- **不要把定時器調回 60 秒。** Firestore **每次查詢至少算一次讀取，即使查不到東西**，
  而一輪同步會發 10 個查詢。舊的 60 秒輪詢等於「整天開著的分頁每天燒掉約 14,000 次
  讀取」，而免費額度是 50,000。現在 15 分鐘的定時器只是監聽器斷線時的救援。
- **同步壞掉時看得出來**：每次成功的時間存進 `SYNC_LAST_OK_KEY`（不是只放記憶體，
  重開才不會退回「等待同步」）。超過一天沒成功就在設定頁明講幾天沒同步、燈號轉琥珀。
  這比列舉錯誤碼重要 —— 登入過期、額度用完、或任何沒想到的原因，都會被這一條接住。
- **換帳號登入會先停下來問**：登出**刻意保留**本機資料（只是想暫停同步的人不該
  失去收藏），所以一台裝置可能存著甲的收藏、乙卻登入了。此時水位線剛被清空，
  直接推送等於把甲的整份收藏送進乙的帳號 —— 所以 `syncNow` 會先比對
  `SYNC_LAST_UID_KEY`，不同就進入 `account-changed`，**不推也不拉**，由使用者選
  「清空本機」或「確定要合併」。清空走 `clearAllData()`，硬刪不寫墓碑，
  **兩邊的雲端都不會被動到**。
- **雲端照片不會自動刪除**：某台裝置刪卡時，別台可能還沒同步。設定頁有手動的
  「清理雲端未使用的照片」。它必須**檔案與 Firestore 中繼資料一起刪**：只刪檔案
  會留下一筆「有照片」的宣告，別台裝置每輪都去拿、每輪都拿到 404。
  相對地，`downloadThumb` 遇到 404 要跳過而不是拋錯 —— 照片的拉取水位線停在
  第一個失敗處，一個不存在的檔案曾經把它後面**所有**照片永久擋住。
  兩邊都要修：刪中繼資料是讓以後不再發生，容忍 404 是讓已經壞掉的裝置自己復原。
- **`seedIfNeeded()` 新增的列要另外推一次**（`pushWholeTables`）。它蓋的是西元
  2000 年的時間戳（刻意的，seeding 必須輸掉每一次合併），那也讓它永遠落在推送
  水位線後面 —— 之後版本新增的預設分類會存在於每台裝置、卻從來不在雲端。
- **預設分類的 id 必須是從名稱推導的**（`builtinId()`，`src/lib/id.ts`）。
  同步是用 id 比對的，所以只要 seeding 用隨機 id，每台裝置就會各自生出一份
  「官方小卡」，而且**每多一台裝置登入就多一整組** —— 這個 bug 實際發生過。
  `src/data/dedupe.ts` 會在每次拉取後依名稱收斂殘留的重複，
  **不要**把它改成一次性的遷移：雲端可能還存著舊的多組 id，而全新裝置
  必然在第一次拉取之前就 seed 完。
- **驅動同步的 `useBackgroundSync()` 掛在 `App.tsx`，不要搬回某個頁面裡。**
  它原本放在設定頁的「雲端同步」區塊，結果 `startAutoSync` 的計時器只在那一頁
  掛載期間存在 —— 在卡片頁新增小卡不會同步，要切回設定頁才會推上去。
  設定頁只用 `useSyncStatus()` 顯示狀態，不驅動任何東西。
- **已登入但還沒拉取過的裝置，開機時不 seed**（`src/main.tsx`）。
  它是要加入一個已經存在的收藏，不是開新的；先 seed 會把使用者早就改名或刪掉的
  預設項目又生回來，而且名稱不同還合併不掉。改由第一輪同步在拉取後才 seed，
  那時 `seedIfNeeded` 看得到既有資料，正確地什麼都不做。

登入採 `signInWithPopup`。**不要改成 `signInWithRedirect`** —— 已在實機 iPhone（加入主畫面的
standalone 模式）驗證過會失敗：轉址流程走得完，但 `getRedirectResult` 回傳空值，
因為 Safari 的追蹤保護把 Firebase 存在 `firebaseapp.com` 名下的暫存狀態跨站隔離了。

**升級 `firebase` 之前，請先用 `public/auth-probe.html` 在真的 iPhone（加入主畫面）上實測。**
這一段的行為只有真機能證明：`signInWithPopup` 在 standalone 模式下可能不是失敗，而是
**永遠不 resolve** —— 視窗有開、帳號也選了，結果卻回不來。實測記錄：10.12.2 與 12.17.1
在測試頁上都能成功登入，所以 SDK 版本本身不是問題。

**登入狀態撐得過完全關閉 App**（2026-08-19，v1.2.x，iPhone 加入主畫面後從 App 切換器
整個滑掉再開）。這一項從 Phase 0 掛到現在都寫著「待確認」，現在確認了：
`browserLocalPersistence` 存在 IndexedDB，和小卡資料同一套儲存，
`navigator.storage.persist()` 一併保護到。原本準備的備案（改成明確提示重新登入）
不需要做。同一輪也走完了三台裝置（iPhone／iPad／電腦）的完整驗收：建卡、
照片縮圖先到再補原圖、改名、刪除，四個方向都傳到了，三台的分類各只有一份。

照片為什麼不用 Firebase Cloud Storage：這個專案啟用 Storage 要求升級到 Blaze（綁信用卡）。
R2 有 10GB 免費、無流量費，且同樣不會因為超量而產生帳單。Worker 以使用者的 Firebase
ID token 驗證身分，**uid 只從 token 的 `sub` 取，絕不從網址取**，所以沒有辦法要到別人的照片。

## 誰可以使用這個雲端空間

**登入 ≠ 可以使用。** 網址與這個 repo 都是公開的，任何人都能用自己的 Google 帳號
通過 Firebase 的驗證 —— 驗證只說明「你是誰」。決定「你能不能在這裡」的是
`firebase/allowlist.json` 這份名單。沒有它，任何找到網址的人都會消耗共用的免費額度，
而額度用完時**所有人一起停止同步**。

名單存的是 **Firebase uid，不是 email**。uid 只是專案內部的不透明識別碼，放進公開
repo 沒有問題；把朋友的 email 寫進公開 repo 則是把別人的個資公開。

### 加一個朋友

1. 請他先登入一次。畫面會顯示「這個帳號還沒有被邀請」以及**他的帳號代碼**，請他複製給你。
2. `npm run allowlist:add -- <uid> "暱稱"`
3. commit + push → Worker 會自動重新部署（照片那一半）。
4. 到 Firebase 主控台 → Firestore → 規則 → 貼上 `firebase/firestore.rules` → **發布**
   （文字資料那一半；規則沒有 CI，只能手動發布）。

`allowlist.json` 是唯一要編輯的地方，`scripts/allowlist.mjs` 會把它產生到
`firestore.rules` 的名單區塊與 `worker/src/allowlist.generated.ts`。
**兩邊都要**：只改規則的話照片還是進得去，只改 Worker 的話文字資料還是進得去。
`npm run allowlist:check` 在 CI 驗證產生結果沒有被手改而漂移。

### 名單是空的代表誰都不能用 —— 包含你自己

這是刻意的預設，不是意外。第一次啟用時就是這樣：部署之後你自己也會看到
「還沒有被邀請」與自己的代碼，把它加進去、再推一次就會恢復。
資料完全不受影響，只是暫停同步而已。

### 每人容量上限

R2 免費 10 GB 是共用的，一個人就塞得滿，所以 Worker 有每人上限
（`LIMIT_BYTES`，預設 1 GiB）。超過時 `PUT` 回 **507**，App 會顯示
「雲端照片空間已滿（已用 x / y）」並指向設定頁的清理功能，而不是無聲失敗。
用量以 R2 的 `list()` 累加，在 isolate 記憶體快取 60 秒 —— 對一個軟性上限來說，
跨 isolate 的些微誤差無所謂，不值得為此引入 KV 或 Durable Object。

粗估：一張卡正反面約 200–400 KB＋縮圖，1000 張卡約 400–800 MB，
所以 10 GB 大約夠 12～15 人。

### 更新既有安裝的資料（重要）

小卡資料存在使用者裝置的 IndexedDB 裡，更新 App 不會碰到它。但**改變資料形狀**時就必須走遷移流程，否則舊資料會用新程式碼讀出錯誤的結果。

分工是：

| 改了什麼 | 要做什麼 |
| --- | --- |
| 只加一個非索引欄位（例如評分） | **什麼都不用做**。IndexedDB 存整個物件，舊資料讀起來就是 `undefined` |
| 加索引或新資料表 | 在 `src/data/db.ts` **新增** `this.version(n).stores({...})`，不要改舊的 |
| 改變既有欄位的意義、改名、換編碼 | 在 `src/data/migrations.ts` 把 `DATA_VERSION` +1，並**附加一個** `MIGRATIONS` 步驟 |

`migrations.ts` 的三條規則：

1. 一個版本一個步驟，**永遠只附加、不修改既有步驟** —— 一定有人還停在前一版。
2. 步驟是對純物件的純函式（不碰 Dexie、不碰 Blob），所以同一份邏輯同時用在啟動時的本機資料和匯入的舊備份上，兩條路徑不可能走歪。
3. 步驟必須可重複執行且防禦性強 —— 它會看到任何舊版寫出來的資料，包含欄位整個不存在的。

安全網（都已實作，不需額外處理）：

- 遷移前會自動把當時的資料存進 `settings`，設定頁出現「升級前的自動備份」讓使用者下載成一般備份檔。**使用者不必事先手動備份也救得回來。**
- 遷移在單一 Dexie transaction 內完成，失敗就整批回滾，不會留下半升級狀態。
- 比本機更新的資料（例如部署被回退）只會被讀取、不會被改寫。
- 匯入備份時，比 App 新的檔案會被擋下並顯示原因；比 App 舊的檔案會先跑遷移再寫入。

改完務必用 `scripts/` 外的 Playwright 腳本實測「舊版建資料 → 換新版 → 資料完好」，不要只靠推論。

### 版本號

`package.json` 的 `version` 是唯一要手動改的地方，設定頁底部顯示成
`v1.0.0 · <commit>`。後面那段 commit 才是真正分辨「跑的是哪一次建置」的東西 ——
Service Worker 可能還在送好幾天前的版本，而畫面上其他地方都看不出來。

| 改什麼 | 版本怎麼動 |
| --- | --- |
| 修 bug、文案 | PATCH（1.0.0 → 1.0.1） |
| 新功能 | MINOR（1.0.1 → 1.1.0） |
| 儲存格式舊版讀不了，或大改版 | MAJOR（1.1.0 → 2.0.0） |

**每一次要推上 `main` 的變更都必須動版本號**，而且在回報時把版本號一起講。
漏掉一次，使用者就得靠 commit 代號自己比對 —— 這正是加版本號要解決的事。
（`1.0.0` → `1.0.1` 這次就漏掉過，換帳號防護那包在線上仍顯示 `v1.0.0`。）
